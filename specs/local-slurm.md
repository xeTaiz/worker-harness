# Local Slurm: implementation, onboarding, and operator handoff

## 1. Read this first

This is the standalone handoff for the **single-user local Slurm feature**, including its client, control plane, and allocation runtime. Another OMP agent can use this document without the original conversation or unpublished plan. S1–S5 are implemented. `feature/local-slurm` is the transfer branch in both repositories; the root pins the exact extension commit. Publication does not mean deployment or live-cluster acceptance.

**Evidence boundary:** the main agent's final native extension suite passed **361 Bun tests, zero failures**, 2,764 expectations across 14 files (2.19 seconds). Actual **OMP 18.14.2 shared-SSH onboarding/migration smoke passed in 32.39 seconds**, including exported native runtime messages; section 9 records its boundaries. The main agent's actual-dotfiles-launcher/private-HOME role-scoped smoke also passed: an unset role retained config/state and persisted writes; `orchestrator`, `worker`, and `unknown-role` could neither see nor mutate those files. Ordinary Work paths stayed available, unrelated `~/.ssh` stayed hidden, `SSH_AUTH_SOCK` stayed unset, and operator environment variables were stripped for those roles. No real host directories or keys were created. Earlier root/runtime/MCP/OMP and per-profile-key onboarding proofs are historical results detailed in section 9. Real login/cluster proof remains pending full sandbox restart and explicit testing; no real IBEX submission, candidate SIF build, fleet deployment, or live V3 acceptance has occurred.

The original checkout and the separate `specs/multi-user.md` work are preserved. This feature does not implement that multi-user plan. Recipient IDs, shared files, shell access, and Tailnet tags are not hostile-user isolation.

### Purpose and scope

Use ordinary Worker Harness (WH) discovery and enqueue to run useful work in **one finite, single-node CPU or multi-GPU Slurm allocation**. Submission uses the user's local OpenSSH configuration, while execution uses the normal WH SIF, daemon, Tailscale SSH, queue, tmux, runner, logs, and notifications. A project and its environment live on shared storage, not in a per-experiment image.

Not included: offline clusters, multi-node distributed jobs, automatic host mounts, dependency scheduling, a separate preparation/submission API, automatic retries/replacements, self-chaining/requeue, login-node services/containers, or multi-user ownership/privacy. No instructions here authorize charged work, broad cancellation, live ACL changes, or production rollout automatically.

## 3. Deploy the matching control plane and runtime, not only the extension

Installing the extension alone is insufficient. The updated server must support reservation/authentication/events/CPU admission, and the SIF must contain the updated entrypoint, daemon, and runner-compatible runtime. An old SIF cannot be made compatible just by updating the client or staging the small shell scripts.

Before deployment, drain affected work, stop the existing control process through its current deployment manager, and take a consistent SQLite backup with its journal state. Preserve its existing registry and Tailscale identity. Run **one control process** against that registry. The local Slurm database changes migrate in place; do **not** apply the separate hierarchical-fleet document's fresh-registry/reset instructions to this rollout.

Existing root recipes (run only as an approved build/deployment operation):

C4
```bash
# Root checkout; no cluster submission occurs in these build recipes.
just build-orch
just build-singularity candidate-local-slurm.sif
# Alternative only after building the matching worker Docker image:
# just build-worker

# Regenerate if start-wh.sh or slurm/wh-allocation.sh changed:
```

`build-singularity` uses the updated `worker_container/Singularity.def`; the alternative uses the locally built Docker worker. Build the candidate once for this runtime release, test/promote it deliberately, and place that exact image on the shared filesystem named by `sif_path`. Record its hash. Do not overwrite the image used by active jobs. Subsequent experiments use this common SIF plus project-local environments; rebuild only for runtime/base dependency changes.

`just build-orch` builds the control image, not a running service. ### Three different credentials and network directions

| Credential / path | Purpose and boundary |
| --- | --- |
| Local cluster SSH private key / SSH agent | User-to-cluster login, inventory, sbatch/squeue/sacct/scancel and shared-file access. Never forwarded or staged in an allocation. |
| `tailnet_key_file` | Local file containing a separately provisioned, non-reusable ephemeral enrollment key restricted to `tag:wh-cluster-job`. A private copy is staged for allocation enrollment, then removed. Not the login key or a fleet/orchestrator key. Provision a fresh usable key when another allocation needs enrollment. |
| `WH_OPERATOR_TOKEN_FILE` / `WH_OPERATOR_TOKEN`; fleet `WH_SESSION_TOKEN` | Client-to-control bearer. Keep outside agent/project/Git roots. Never stage it on shared storage or pass it into an allocation. |
| Per-reservation worker token | Client generates/persists 32 random bytes; server stores its SHA-256. Scoped to registration of that reserved worker, not control authority. Staged copy is cleaned at exit and server revokes on confirmed terminal accounting. |

The human client uses `WH_ORCHESTRATOR_URL` on privileged control **12889**, plus valid existing operator/session credentials. New reservation/observation/event routes require credentials even in legacy anonymous development mode. A profile's `orchestrator_host` is only a hostname/IP, without scheme/port; `orchestrator_registration_port` defaults to **12888**. Cluster workers can reach registration 12888, not control 12889. The orchestrator must reach their Tailnet SSH **22**, with the runtime user permitted by Tailscale SSH policy. Tailnet enrollment/control-server reachability must work from compute nodes, not just the login node. HTTP control assumes the trusted private Tailnet; do not move it to an untrusted/public network without a separate secure deployment design.

C6
```bash
export WH_ORCHESTRATOR_URL='http://YOUR_ORCHESTRATOR_TAILNET_NAME:12889'
export WH_OPERATOR_TOKEN_FILE="$HOME/.config/worker-harness/operator.token"
```

Create/distribute the protected credential out of band, not by pasting its value into this document, command arguments, shell history, or Git. Fleet clients use their supplied session token and do not fall back to the operator token. Review `headscale-policy.example.json` against broader existing rules: example tags do not remove preexisting broad grants, and no code applies live policy automatically.

## 4. Interactive `/cluster-add`: configure first, then install SSH trust

Run this in an ordinary interactive OMP session after loading the checkout:

C7
```text
/cluster-add
```

`/cluster-add ibex-cpu` supplies the ID and skips that one prompt. Reusing an existing profile is a separate dialog choice, not an SSH/network operation.

The staged dialog validates a complete profile before explicit final confirmation. It does not submit work or run remote setup. Cancelled/invalid input must not install a partial profile. The default destination is `${XDG_CONFIG_HOME:-$HOME/.config}/worker-harness/clusters.json`; `WH_CLUSTER_CONFIG` selects an alternate file. Missing file means no cluster targets; unreadable, malformed, unknown-field, or inconsistent configuration is an explicit error, never silently ignored.

Supply operator-known values, not guessed IBEX defaults:

1. A unique profile ID, description including site preemption/utilization/account limits, and GPU or CPU compute kind.
2. Existing SSH alias/direct login destination, or an existing profile's connection for another partition on the same site. Supply login user/port where requested. Existing aliases preserve their ProxyJump/ControlMaster/site policy.
3. Shared storage ID, existing cluster-host shared root, and exact candidate SIF path. CPU/GPU profiles sharing one filesystem use the same storage ID/root/SIF.
4. Installed runtime (`apptainer` or `singularity`) and any trusted site module/setup prelude; account and the actual authorized partition. GPU profiles need exact GRES GPU type and positive maximum GPUs; CPU profiles require `max_gpus: 0` and omit `gpu_type`.
5. Explicit maximum walltime, site-permitted failure grace (zero when idle holding is forbidden), termination grace, enrollment key file/login server, and orchestrator registration hostname/port.
6. Optional advanced QoS, simple feature constraint, CPU/RAM caps, warning and poll intervals. Defaults are warning 120 seconds, registration 12888, polling 15 seconds; these are software defaults, not an assertion of site permission.
7. Review the profile, key/SSH actions and commands; use edit-field or cancel if needed, then explicitly confirm the unencrypted-key warning. No key generation, local file writes, or process spawning occurs before that confirmation. Optional fields can be cleared with `-` in the advanced flow. No credential value belongs in the profile.

The flow manages **one shared Ed25519 login identity** for all onboarded clusters: `dirname(clusters.json)/id_ed25519` and `id_ed25519.pub`, plus `dirname(clusters.json)/known_hosts`. These shared files live directly in `~/.config/worker-harness` by default, **not** in its `ssh/` subdirectory; `XDG_CONFIG_HOME` and `WH_CLUSTER_CONFIG` select the actual configuration parent. Connection-specific `config` and `bootstrap_config` remain under `ssh/<profile-id>/`; connection reuse may retain the first profile's config path. Keeping shared files outside `ssh/` avoids collisions with valid legacy profile IDs such as `id_ed25519` or `known_hosts`. Directories are 0700 and generated files 0600. Existing shared key/trust files are reused, never overwritten. A profile's `ssh_config_file` selects its config through OpenSSH argv `-F`, without editing `~/.ssh/config`. Alias mode preserves ordinary user config/ProxyJump/ControlMaster policy. `/etc/ssh/ssh_config` is explicitly included only when readable, regular, root/current-UID owned and not group/world writable; otherwise a durable warning directs required site settings into user config. Strict OpenSSH checks on user config are not weakened. Direct mode creates a unique `wh-<id>` alias with the supplied hostname/user/port and optional ProxyJump.

A newly generated shared private key is initially **unencrypted**; the dialog warns before generating it and never captures a passphrase. An existing shared key, including an encrypted one, is preserved. Add a passphrase in your own terminal with `ssh-keygen -p -f <printed-shared-key-path>` if desired, then unlock it through an accessible dedicated agent. **Read the sandbox restart/agent gate below before doing this:** the current launcher unsets `SSH_AUTH_SOCK`, so a host `ssh-add` does not by itself make the key usable inside this sandbox. BatchMode cannot unlock a key or answer MFA; resolve agent/site policy explicitly without weakening authentication.

Onboarding prints commands; **it does not execute them**. Both the dedicated `config` and `bootstrap_config` explicitly use the shared configuration-parent `known_hosts` via `UserKnownHostsFile`. Its initial empty 0600 file is created only if absent; no user/global host-trust database is automatically copied, replaced or cleared. Existing independently verified entries may be copied manually after review. First connect with `bootstrap_config` and independently compare the site's fingerprint before accepting it into this managed trust file; `ssh-keyscan` alone is not verification. A newly added profile's bootstrap retains target/user/includes and existing key/agent/password/MFA authentication without the new IdentityFile/IdentitiesOnly restriction. Migration bootstrap additionally retains the old profile key via explicit IdentityFile, **without** IdentitiesOnly, so hosts previously authorizing only that key remain accessible while installing the shared key. Install **only the shared public key** with the printed `ssh-copy-id -F <bootstrap_config> -i <shared-public-key> <alias>` or manual authorized_keys alternative. The dedicated config selects the shared IdentityFile with IdentitiesOnly; require its printed probe using `BatchMode=yes`, `StrictHostKeyChecking=yes`, and `ConnectTimeout=10`. Never bypass a changed/missing trusted host key. No private key, enrollment value or control bearer belongs in Git or an allocation.

Manual command shape (substitute the exact paths/alias printed by onboarding; no command below is run by the dialog):

C16
```bash
WH_CONFIG_DIR='/absolute/configuration/directory/from/onboarding'
SSH_DIR="$WH_CONFIG_DIR/ssh/ibex-cpu" # Use the exact connection directory printed.
SSH_ALIAS='EXACT_PRINTED_ALIAS'
# First connect interactively; accept a host key only after independent fingerprint comparison.
ssh -F "$SSH_DIR/bootstrap_config" "$SSH_ALIAS"
# Install the public key using existing account authentication, not the new identity yet.
ssh-copy-id -F "$SSH_DIR/bootstrap_config" -i "$WH_CONFIG_DIR/id_ed25519.pub" "$SSH_ALIAS"
# Protect the generated private key in your own terminal.
ssh-keygen -p -f "$WH_CONFIG_DIR/id_ed25519"
# Only after dedicated-agent access has been provisioned for this sandbox:
ssh-add "$WH_CONFIG_DIR/id_ed25519"
ssh -F "$SSH_DIR/config" -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=10 "$SSH_ALIAS" true
```

An already running OMP process cannot inherit a newly selected agent environment. Under the current sandbox launcher, restarting OMP or merely exporting a host socket is insufficient; follow the dedicated-agent and full-sandbox restart gate below.

For IBEX, obtain the real login alias, account, CPU partition, GPU partition/type/caps, runtime modules and site policy first. Add the GPU or CPU profile, then rerun `/cluster-add` for the other kind and reuse its connection/storage. The name `ibex-cpu` is only a local profile ID: it is **not** a guessed partition name. Onboarding makes local configuration and SSH setup easier; it cannot establish remote filesystem identity, install the runtime, authorize account access, or prove compute-node Tailnet reachability.

### Migrate existing per-profile keys explicitly

After the persistence/restart gate below, run this interactive OMP command:

```text
/cluster-ssh-migrate
```

If there is no shared key yet, select **one** existing wizard-managed legacy key for promotion and confirm. The migration exclusively copies its bytes into the shared path, preserving an encrypted key as encrypted; it does not generate a second shared identity, overwrite an existing shared key, or delete legacy keys. If a shared key already exists it is reused. Only recognized wizard-generated managed configs are migrated; external/unrecognized configs are explicitly skipped rather than guessed or overwritten. Review the command's reported migrated/skipped profiles.

Migration rewrites recognized dedicated configs to the shared identity/trust while retaining their alias/direct destination policy. Each migrated bootstrap config retains its **old per-profile IdentityFile without IdentitiesOnly**, alongside shared host trust, to authorize installation on hosts that accepted only the old key. It prints bootstrap first-connect, shared-public-key installation, and strict dedicated-config probe commands for each distinct migrated host. A cluster previously authorized with a different profile key needs the **shared** public key installed; updating local config alone cannot authorize it. Host trust is not imported automatically: review/copy only independently verified entries or verify each host interactively using the printed bootstrap config. Keep the old files until all required hosts pass the strict shared-key probe. Merely adding sandbox path entries does not migrate existing profiles.

### Persistent sandbox configuration and restart gate

The actual agent-sandbox allowlist is `~/dotfiles/agent-sandbox/.config/agent-sandbox/paths`. Its two Worker Harness entries are **`human:~/.config/worker-harness`** (profiles, managed login key/configs, host trust and any enrollment credential stored there) and **`human:~/.local/state/worker-harness`** (submission journals, scoped tokens and notification cursors). The launcher strips `human:` and applies normal path validation only for a human launch with `WH_SESSION_ROLE` unset or empty. Any nonempty role, including `orchestrator` or an unknown role, skips those entries entirely; stripping operator environment variables alone would not protect files in these directories. Unmarked legacy entries remain shared and unchanged. Empty or malformed marked paths fail human-launch validation, never become unmarked fallback binds. This is a narrow credential-mount boundary, not hostile-user isolation or protection against a separately allowlisted parent directory. Allowlist changes do not alter existing sandbox mounts; absent host source directories are skipped, not created.

Ensure the next host launch uses **both** edited files: invoke **`"$HOME/dotfiles/agent-sandbox/.local/bin/agent-sandbox"`** with the usual tool/binary arguments, and set **`AGENT_SANDBOX_PATHS="$HOME/dotfiles/agent-sandbox/.config/agent-sandbox/paths"`** in its host environment. Alternatively, update the host's stow/symlink installation for both launcher and allowlist, and verify both active paths resolve to these edited files. An older installed launcher rejects `human:` syntax; pointing only its allowlist at the new file is insufficient. This session has not established the host's active launcher/config symlinks.

Before the next sandbox launch, run this **in a host terminal outside the existing sandbox**, using the host account that launches it:

```bash
mkdir -p "$HOME/.config/worker-harness" "$HOME/.local/state/worker-harness"
chmod 700 "$HOME/.config/worker-harness" "$HOME/.local/state/worker-harness"
```

Do not create these in the current masked sandbox HOME and assume they exist persistently on the host. The current sandbox's missing default configuration directory does not establish whether the host already has profiles, keys or journals; inspect those only from the host terminal, without exposing secrets.

With custom `XDG_CONFIG_HOME`, `WH_CLUSTER_CONFIG`, `XDG_STATE_HOME`, or `WH_CLUSTER_STATE_DIR`, persist the **actual** configuration/managed-SSH and state locations instead: add their host paths with the same **`human:` prefix**, create their host directories with private permissions before launching, and preserve the overrides in the new human session. Do not expose a broader unmarked parent directory or other credentials to fleet roles. The two default entries alone do not cover arbitrary override paths.

**Stop here for restart:** fully exit and relaunch **agent-sandbox**, then start OMP inside the new sandbox. Restarting only OMP cannot apply the new mounts. Existing legacy profiles also require the explicit SSH migration above; mounting new directories alone cannot fix stale `ssh_config_file`, key or known-host paths. Do not rerun onboarding or attempt live SSH from the old sandbox to work around missing mounts.

The launcher currently unsets `SSH_AUTH_SOCK`. An encrypted login key therefore additionally requires a deliberately provisioned **dedicated** agent/socket made accessible to the new sandbox and explicitly selected for its SSH client. Merely running `ssh-add` in a host shell, restarting OMP, or restarting the unchanged launcher does not make that agent accessible. Do not forward the general host agent or change launcher/forwarding policy as part of this migration. Without dedicated-agent access, a passphrase-protected key is a visible prerequisite failure for BatchMode, not a reason to weaken authentication.

The main agent's **actual edited dotfiles launcher plus actual allowlist** passed a private-HOME role-scoped smoke: with `WH_SESSION_ROLE` unset, config/state files were visible and writes persisted outside the sandbox fixture; with `orchestrator`, `worker`, or `unknown-role`, those files were hidden and could not be mutated. Ordinary Work paths remained available in every specimen, unrelated `~/.ssh` stayed hidden, `SSH_AUTH_SOCK` remained unset, and operator environment variables were stripped for the role specimens. This did not create real host directories, load real keys or exercise real login. The final native extension suite passed 361 tests, and actual OMP 18.14.2 onboarding/migration smoke passed locally. After restart and migration, require the strict printed login probe with independently reviewed host trust; real login/cluster acceptance remains pending and is not implied by local fixture/source/UI tests. This gate does not authorize a charged allocation.

## 5. Shared storage and environment preparation

At least one **existing participating WH worker** and the cluster must already mount the same filesystem. The original test/source worker need not. Configure `WH_SHARED_ROOTS_JSON` on participating fleet hosts using each host's actual directory; the cluster profile supplies its cluster-host `shared_root`. Both become `/data/shared/ibex` for these profiles. This is a bind of an existing directory, not a mount/transfer service. Preserve unrelated `WH_EXTRA_BINDS`.

C9
```bash
# Example only: participating fleet host, before its approved restart.
export WH_SHARED_ROOTS_JSON='{"ibex":"/OPERATOR_EXISTING_HOST_MOUNT"}'
```

Use `list_data` to find that worker; discovery lists immediate non-symlink directories, so an entirely empty collection may not appear. Prove backing identity with a random probe, not matching path spelling. Through **ordinary WH `exec` on the participating worker**, run:

C10
```bash
python3 - <<'PY'
import json, secrets
from pathlib import Path
p = Path('/data/shared/ibex') / ('.wh-storage-probe-' + secrets.token_hex(16))
token = secrets.token_hex(32)
with p.open('x') as f:
    f.write(token + '\n')
print(json.dumps({'probe_name': p.name, 'token': token}))
PY
```

From the submitting machine use the profile's exact SSH host/config to read that filename under `shared_root`, compare its content to the returned token, and require equality. Then remove that exact file through ordinary WH exec regardless of success. A missing/different token blocks reuse. The cluster enqueue path also performs its identity check; do not bypass it. Use ordinary `upload_file` / `data_copy` to bring source, lockfiles and data from a nonparticipating test worker to this worker. Never copy a virtualenv from another absolute path/architecture.

C17
```bash
# Local submitting shell; use the dedicated config/alias printed by onboarding.
SSH_CONFIG='/absolute/path/from/onboarding/ssh/ibex-cpu/config'
SSH_ALIAS='EXACT_PRINTED_ALIAS'
probe_name='PASTE_RETURNED_RANDOM_PROBE_NAME'
expected='PASTE_RETURNED_RANDOM_TOKEN'
# Replace this example root with the profile's exact cluster shared_root.
actual=$(ssh -F "$SSH_CONFIG" -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -o ConnectTimeout=10 "$SSH_ALIAS" "cat -- '/OPERATOR_SHARED_ROOT/$probe_name'") &&
  test "$actual" = "$expected"
```

Clean up through the same participating worker's ordinary `exec`, with the exact returned filename: `rm -- /data/shared/ibex/RETURNED_RANDOM_PROBE_NAME`. This removes only the random probe, not the collection or project.

Prepare projects under `/data/shared/ibex/projects/<project>`. For uv projects, the SIF already contains uv; record the SHA-256 of the **exact common SIF**, lockfile, architecture and container Python major/minor. Through ordinary exec on a worker using that SIF, or as a queued **CPU preparation job with no environment_path yet**, use:

C11
```bash
set -eu
cd /data/shared/ibex/projects/OPERATOR_PROJECT
SIF_SHA256='PASTE_EXACT_COMMON_SIF_SHA256'
```

### Submission and recovery sequence

1. Validate current live inventory, resources, paths and shared identity; generate/persist a submission key and canonical request digest.
2. Reserve a real OFFLINE worker with scoped registration token hash; persist its initial ordinary queued job with matching submission key. Idempotent same-key/same-body requests recover the same worker/job; changed payload conflicts. Never sbatch without confirmed attached useful work.
3. Stage private run files and small root-owned runtime assets at `<shared_root>/.wh-slurm/<worker_id>`, then submit once through local strict OpenSSH. Remote flock, attempt marker, and atomic `submitted.json` fence retries. Patch `submission_attempted` before sbatch. Inherited `SBATCH_*` and dangerous Slurm option variables are removed; use `SLURM_UMASK=077` and `--export=NIL` while retaining site authentication/runtime environment.
4. Registration on 12888 must authenticate the reserved identity/capacity. Actual resource mapping and orchestrator-to-worker Tailscale SSH readiness gate ONLINE/queue dispatch. A Tailnet IP alone is insufficient. Startup/enrollment is bounded by 180 seconds.
5. Queue-managed useful work runs through the existing daemon/JobManager/tmux/runner. CPU jobs have zero GPUs, empty CUDA mask, and serialize one at a time on CPU Slurm targets; arbitrary fleet zero-GPU enqueue is not enabled. GPU assignments preserve Slurm visibility across cleanenv and resolve physical UUIDs; missing/ambiguous/MIG mappings fail visibly. CPU mode omits `--nv` and CUDA readiness. CPU/memory reports reflect allocation limits.
6. Normal success with no useful queue/running work atomically closes admission (DRAINING), then exits. Failed queued work permits only the configured bounded failure grace; zero means no idle holding. Ordinary exec diagnoses but does not extend grace. An actually starting queued CPU/GPU rerun clears it. The deadline derives from runner finish time and survives reconnect/outage. Immediate diagnostic exec is not useful queued work.
7. Scheduler polling reports raw states/reasons/timestamps and recovered structured job results before terminal reconciliation. Confirmed results cannot be rewritten by terminal accounting or stale observations. SSH failure, missing squeue entries, or heartbeat loss is not completion. Completed/reserved worker history survives pruning, but finished/DRAINING targets reject admission with `409 SLURM_WORKER_FINISHED`; use fresh cluster enqueue.

On uncertainty, retain the returned/generated `submission_key` and inspect ordinary worker/job/scheduler evidence. Retrying the same request/key reads journal/remote evidence and exact owned scheduler identity; it never blindly resubmits after an attempt marker. Multiple matches require a validated `candidate_job_id` from evidence; candidate selection is excluded from the digest and requires an existing key. Read tools never bind/submit. A new key intentionally means a new experiment, not recovery of the unknown one.

`stop_job` defaults to `scope: "job"`; other useful queued/running work is preserved. Cancelling the last pending job can atomically close/cancel an empty not-yet-started allocation. `scope: "allocation"` derives/validates the scheduler allocation from the job, closes admission and requests local scancel; response means requested until terminal accounting. This scope is rejected for non-Slurm workers. Initial GPU count/worker reassignment freezes once submission is attempted: cancel/fresh enqueue to change allocation resources. Never perform broad name-based scancel.

### Runner, failure grace, and signals

`src/worker_harness/job_runner.py` is the shared standalone primitive, not another allocation supervisor. `run --job-dir PATH` is a Linux child subreaper, writes output plus atomic runtime/result evidence, and proves descendants exited before release. `control --job-dir PATH --action stop|checkpoint --signal USR1|TERM` uses a private socket and verified pidfds; stop uses TERM, two-second grace, then KILL. Missing proof retains claims; printed `EXIT:` text is not proof.

The finite shell wrapper owns traps, a background child and interruptible wait. USR1 warning closes admission and forwards the workload-declared checkpoint signal. TERM is sticky and dominates later checkpoint signals, bounds cooperation by site termination grace, then stops/reaps. Persistent control files cover pre-daemon signals. Checkpoint saving/resume is application code with shared paths; forwarding a signal never proves a checkpoint exists. Site preemption can give less/no warning. Useful queued work can finish during outages, but unknown remote queues do not authorize idle holding or extend persisted failure deadlines. Requeue/repeated launch markers are rejected. There is no successor sbatch.

### CPU/GPU resource sizing

Live `sinfo --Node`, named-field `scontrol --oneliner show nodes` and partition policy drive sizing. Exact partition/GPU type and simple feature or `&` conjunction constraints filter eligible configured nodes. Busy eligible nodes still count for sizing; availability/free resources are a separate timestamped observation. Missing/nonpositive/ambiguous/MIG capacity fails instead of guessing. Optional IBEX `ginfo` is bounded supplemental availability, never the capacity source or prerequisite.

For requested GPUs `g`, require `1 <= g <= max_gpus` and nodes with at least g of that type. For node i, C is configured schedulable CPUs, M is RealMemory minus MemSpecLimit (MiB), and G is configured physical GPUs. Defaults are `cpus=max(1,floor(g*min(C/G)))` and `memory_mb=256*floor(g*min(M/G)/256)`. Thus an 8-GPU/64-CPU/524288-MiB node yields 8 CPUs/65536 MiB for one GPU, 16/131072 for two, independent of current free capacity. Heterogeneous nodes use conservative minima, not a largest-node/average guess.

CPU defaults are 1 CPU/4096 MiB with no GPUs. Profile/partition CPU caps apply first, then RAM caps including final CPUs times MaxMemPerCPU. Computed defaults may cap/round down; explicit impossible requests fail, never silently shrink. Require a matching node able to fit the final request and bound explicit walltime by profile/partition MaxTime. Unknown account/QoS restrictions remain unverified until Slurm responds. Fresh SSH/inventory failure blocks submission.

Emit exactly `--nodes=1 --ntasks=1 --cpus-per-task=<n> --mem=<MiB>M`, plus `--gpus-per-node=<type>:<g>` only for GPU work, explicit time, `--parsable --no-requeue --export=NIL`, unique name/comment and shared logs. Do not use exclusive, `--mem=0`, or mixed per-GPU/per-task CPU/RAM forms.
