# Local Slurm: implementation, onboarding, and operator handoff

## 1. Read this first

This is the standalone handoff for the **single-user local Slurm feature**, including its client, control plane, and allocation runtime. Another OMP agent can use this document without the original conversation or unpublished plan. S1–S5 and the approved minimal, resumable SSH-first onboarding/additional-filesystem changes are implemented and locally verified. Current evidence is **485 Bun tests (3,805 assertions/16 files, 8.09s)**, **seven local rolling-stderr process-boundary smoke cases**, actual **Python 3.9.23 emitted-script client tests (47 passed, 363 assertions, 2.52s) plus 11 local visibility/failure-boundary verifier smoke cases**, **339 isolated root Python tests**, prior actual **OMP 18.14.2/native-PTY plus private local SSH bootstrap proof (14.29s)** and actual **multiple-filesystem launcher smoke (1.70s)**; section 9 separates historical workflow proofs and records boundaries. `feature/local-slurm` is the transfer branch in both repositories; the root pins the exact extension commit. Publication is pending the parent handoff and does not mean deployment or live-cluster acceptance.

**Historical evidence boundary (recorded 2026-11-01; predates this minimal-workflow change):** the prior native extension suite passed **361 Bun tests, zero failures**, 2,764 expectations across 14 files (2.19s); prior actual **OMP 18.14.2 shared-SSH/migration smoke passed in 32.39s**. Those remain historical evidence, not the new proof. The restored launcher/private-HOME proof passed with the two plain config/state paths and separate source-generated fleet allowlists. The live production control OpenAPI is reachable (HTTP 200) but lacks reservation, Slurm-update and job-events routes: **updated server deployment is a hard enqueue prerequisite**. Candidate SIF build/execution and real Slurm/Tailnet/charged acceptance remain unperformed.

The original checkout and the separate `specs/multi-user.md` work are preserved. This feature does not implement that multi-user plan. Recipient IDs, shared files, shell access, and Tailnet tags are not hostile-user isolation.

### Purpose and scope

Use ordinary Worker Harness (WH) discovery and enqueue to run useful work in **one finite, single-node CPU or multi-GPU Slurm allocation**. Submission uses the user's local OpenSSH configuration, while execution uses the normal WH SIF, daemon, Tailscale SSH, queue, tmux, runner, logs, and notifications. A project and its environment live on shared storage, not in a per-experiment image.

Not included: offline clusters, multi-node distributed jobs, automatic host mounts, dependency scheduling, a separate preparation/submission API, automatic retries/replacements, self-chaining/requeue, login-node services/containers, or multi-user ownership/privacy. No instructions here authorize charged work, broad cancellation, live ACL changes, or production rollout automatically.

## 2. Transfer the two repositories and replace the local OMP plugin

Root origin is `git@github.com:xeTaiz/worker-harness.git`. The publisher must commit/publish the extension first, then commit/publish the root with that exact gitlink. No literal revision is needed inside this document: the reviewed root commit plus its pinned submodule commit identify the release without a self-referential commit hash.

On the receiving machine:

C1
```bash
git clone --branch feature/local-slurm --recurse-submodules \
  git@github.com:xeTaiz/worker-harness.git worker-harness-local-slurm
cd worker-harness-local-slurm
git submodule update --init --recursive
```

Use the extension's **detached checkout at the root-pinned commit** for the safest installation. Do not automatically switch it to the latest branch tip: that can change the reviewed root/extension pairing. The clone uses your existing GitHub access, not the cluster login key generated by onboarding. If continued extension development is intended, deliberately create a local branch from the pinned commit; alternatively fetch and switch to the published extension branch after reviewing any difference:

C2
```bash
git -C extensions/pi-worker-harness fetch origin feature/local-slurm
git -C extensions/pi-worker-harness switch --track origin/feature/local-slurm
```

That `--track` form assumes the local branch does not exist. For an existing branch, switch to it without discarding local edits. Root and extension commits/pushes remain separate; update the root gitlink only after the new extension commit is available remotely. Do not copy dirty worktrees, private keys, `.env`, profile files, state journals, SIFs, caches, or token files into Git.

## 3. Deploy the matching control plane and runtime, not only the extension

Installing the extension alone is insufficient. The updated server must support reservation/authentication/events/CPU admission, and the SIF must contain the updated entrypoint, daemon, and runner-compatible runtime. An old SIF cannot be made compatible just by updating the client or staging the small shell scripts.

Both image definitions carry the static capability label **`org.worker-harness.slurm-runtime=1`**. Onboarding may inspect an existing SIF read-only with `apptainer inspect --json` or `singularity inspect --json`; it must not execute a container on a login node. A filename alone is not compatibility evidence. The label permits static discovery, not a claim of successful compute-node execution. Build the updated candidate and deploy the matching server before enqueue. Missing image/runtime, unavailable credentials or missing control API routes save a **blocked, resumable setup draft**, never a fabricated ready cluster profile.

Before deployment, drain affected work, stop the existing control process through its current deployment manager, and take a consistent SQLite backup with its journal state. Preserve its existing registry and Tailscale identity. Run **one control process** against that registry. The local Slurm database changes migrate in place; do **not** apply the separate hierarchical-fleet document's fresh-registry/reset instructions to this rollout.

Existing root recipes (run only as an approved build/deployment operation):

C4
```bash
# Root checkout; no cluster submission occurs in these build recipes.
just build-orch
just build-singularity candidate-local-slurm.sif
# Alternative only after building the matching worker Docker image:
# just build-worker
# just build-singularity-from-docker candidate-local-slurm.sif
# Regenerate if start-wh.sh or slurm/wh-allocation.sh changed:
just package-slurm-client
sha256sum candidate-local-slurm.sif
```

`build-singularity` uses the updated `worker_container/Singularity.def`; the alternative uses the locally built Docker worker. Build the candidate once for this runtime release, test/promote it deliberately, and place that exact image on the shared filesystem named by `sif_path`. Record its hash. Do not overwrite the image used by active jobs. Subsequent experiments use this common SIF plus project-local environments; rebuild only for runtime/base dependency changes.

`just build-orch` builds the control image, not a running service. For a site using the checked-in Compose template, preserve the actual existing volume/bind mounts, Tailnet env, private credentials, inventory, and network configuration. Set `WH_ORCHESTRATOR_IMAGE` to the reviewed immutable image, then use the documented template commands below; another deployment manager should perform its equivalent replacement instead. Stop the previous instance first, and do not delete volumes. The optional web edge is not needed for this feature.

C5
```bash
docker compose -f docker-compose.orchestrator.example.yml config --quiet
docker compose -f docker-compose.orchestrator.example.yml up -d
```

The template also needs its existing `WH_TAILNET_ENV_FILE`, `WH_TAILSCALE_VOLUME`, `WH_REGISTRY_VOLUME`, inventory/agent/service-SSH paths, `WH_OPERATOR_TOKEN_FILE`, and fleet settings. For this rollout `WH_REGISTRY_VOLUME` denotes the preserved registry, not a new empty one. Keep prior images and backup for rollback. Never expose API ports publicly. Existing participating fleet workers can use the documented transactional `just deploy <ssh-target>` / `just deploy-local` or image-administration tools in an approved rollout; do not silently restart active work. Their launcher/shared-bind configuration must expose the collection used below.

### Three different credentials and network directions

| Credential / path | Purpose and boundary |
| --- | --- |
| Local cluster SSH private key / SSH agent | User-to-cluster login, inventory, sbatch/squeue/sacct/scancel and shared-file access. Never forwarded or staged in an allocation. |
| `tailnet_key_file` | Local file containing a separately provisioned, non-reusable ephemeral enrollment key restricted to `tag:wh-cluster-job`. A private copy is staged for allocation enrollment, then removed. Not the login key or a fleet/orchestrator key. Provision a fresh usable key when another allocation needs enrollment. |
| `WH_OPERATOR_TOKEN_FILE` / `WH_OPERATOR_TOKEN`; fleet `WH_SESSION_TOKEN` | Client-to-control bearer. Keep outside agent/project/Git roots. Never stage it on shared storage or pass it into an allocation. |
| Per-reservation worker token | Client generates/persists 32 random bytes; server stores its SHA-256. Scoped to registration of that reserved worker, not control authority. Staged copy is cleaned at exit and server revokes on confirmed terminal accounting. |

The human client uses `WH_ORCHESTRATOR_URL` on privileged control **12889**, plus valid existing operator/session credentials. New reservation/observation/event routes require credentials even in legacy anonymous development mode. A profile's `orchestrator_host` is only a hostname/IP, without scheme/port; `orchestrator_registration_port` defaults to **12888**. Cluster workers can reach registration 12888, not control 12889. The orchestrator must reach their Tailnet SSH **22**, with the runtime user permitted by Tailscale SSH policy. Tailnet enrollment/control-server reachability must work from compute nodes, not just the login node. HTTP control assumes the trusted private Tailnet; do not move it to an untrusted/public network without a separate secure deployment design.

C6
```bash
export WH_ORCHESTRATOR_URL='http://YOUR_ORCHESTRATOR_TAILNET_NAME:12889'
export WH_OPERATOR_TOKEN_FILE="$HOME/.config/worker-harness/operator.token"
```

Create/distribute the protected credential out of band, not by pasting its value into this document, command arguments, shell history, or Git. Fleet clients use their supplied session token and do not fall back to the operator token. Review `headscale-policy.example.json` against broader existing rules: example tags do not remove preexisting broad grants, and no code applies live policy automatically.

## 4. Interactive `/cluster-add`: SSH first, discover, then review

Run this in an ordinary interactive OMP session after loading the checkout:

C7
```text
/cluster-add
/cluster-add ibex
```

The argument names a cluster setup or resumes its saved draft; it is not a required CPU/GPU target ID. With no argument, existing drafts can be selected. The wizard never submits an allocation, installs software remotely, or deploys the control plane.

The minimal sequence is:

1. Enter an existing SSH alias or `user@host`. Local OpenSSH `-G` resolves user, port and jump policy; a separate username question is conditional when resolution cannot supply it. Reuse an unambiguous managed connection automatically. Review the suggested short hostname/name (or command argument), then optionally describe the site.
2. Explicitly consent to managed shared-key/trust setup before local credential creation. Setup prepares the managed files, saves phase `ssh`, publishes only short fenced shell commands, and returns. Command 1 installs the shared public key; command 2 verifies/adds shared host trust only when needed. No test/select dialog covers the instructions. The wizard does not execute these commands or autoaccept host trust.
3. Run the commands in your own terminal, independently verify any host fingerprint, then submit `/cluster-add <name>` again (prefilled where supported). This fresh invocation performs one strict BatchMode probe without a bootstrap modal. A failed probe republishes relevant commands, warns and retains the private draft without a retry loop or discovery. Older saved SSH drafts use this same resume path; successful SSH continues below.
4. After SSH succeeds, select an existing WH shared path from `list_data`, or type `/data/shared/<storage_id>`, and enter its exact existing **cluster-host root**. Explicitly answer **“Add another filesystem mapping?”**; each yes repeats those same two fields. The first mapping remains the primary run/staging root; every additional mapping is retained in `additional_shared_roots`. Each mapping must pass backing-identity verification against a participating WH worker using a temporary random probe and cleanup.
5. Bounded read-only SSH discovery inspects Slurm inventory/partition limits, account/default/QoS evidence, installed runtime/version and compatible SIF labels. No allocation, recursive filesystem scan or login-node container execution is used.
6. Resolve only missing information: e.g. a trusted runtime/module prelude, candidate SIF path or an explicit billing choice required by the site. Visible accounts/QoS do not authorize choosing an arbitrary, premium or special one. Prefer the known default account; omit `account` when Slurm should select its default. Hidden association data remains marked unknown. Do not repeat upfront CPU/GPU/type/capacity/account/limits questionnaires.
7. Review one editable summary and the generated safe CPU/GPU target set. Discovery derives CPU targets from supported CPU partitions and GPU targets per partition/exact physical GPU type using configured capacity, not currently free resources; ambiguous/MIG configurations remain unsupported evidence. Advanced settings are optional, not a mandatory menu. Save the complete validated target set atomically, with deterministic unique IDs and the same shared connection, trust and mappings.

The default **allocation ceiling** is **604800 seconds (seven days)**, clamped downward by a finite partition MaxTime. It is not a requested allocation duration and never supplies a missing job duration: every enqueue still explicitly supplies `slurm.walltime_seconds`. Defaults are failure grace **0**, termination grace **20**, warning **120**, polling **15** seconds and registration port **12888**. Any positive failure grace, including the optional 300-second setting, requires explicit Advanced opt-in and a site idle-policy warning.

Completed targets remain version-1 profiles at `${XDG_CONFIG_HOME:-$HOME/.config}/worker-harness/clusters.json`, overridden by `WH_CLUSTER_CONFIG`. Private version-1 drafts are in **`dirname(clusters.json)/setup-drafts.json`** (0600), separate from completed profiles and submission journals; incomplete/blocked drafts never appear as compute targets. Cancel before initial key-setup consent creates no credentials or completed profile. After consent, cancel reports the retained key/draft and preserves the last valid stage; cancellation aborts active discovery where supported. Invalid/unreadable/inconsistent completed configuration remains an explicit error, never an empty target list.

Global cluster integration settings live in **`dirname(clusters.json)/cluster-integration.json`** (version 1, private 0600), collected once and reused: a **Tailnet key file path** and login server, plus an optional orchestrator registration override. Existing explicit integration/profile settings are reused. The registration default is the active control URL's hostname on **12888**, never worker access to privileged control **12889**. Only file existence/private permissions are inspected; no plaintext secret prompt or reading arbitrary `worker-harness.env` secrets, and no claim that enrollment thereby succeeds. Missing deployment/credential prerequisites retain a blocked resumable draft.

Readiness first requires existing control Authorization from the API credential contract (`WH_OPERATOR_TOKEN_FILE`, `WH_OPERATOR_TOKEN`, or an authorized session), then the required OpenAPI routes. Missing authorization blocks the draft; there is no token-value prompt. A missing Tailnet key file can be provisioned at its saved path before resuming, with a conditional file-path correction only when needed. After a filesystem-identity failure, resume offers **Retry saved mappings / Edit filesystem mappings / Save and exit**; editing repeats the same catalogue/root/add-another loop. Wizard runtime-prelude edits permit safe module loads/generated PATH setup, not arbitrary login-node shell execution; manual-profile `runtime_setup` remains trusted operator configuration.

Credential presence alone does not pass readiness. After checking required live OpenAPI routes, setup performs a bounded authenticated `GET /api/v1/job-events?recipient_id=wh-setup-<fresh UUID>&after=0`; only HTTP200 passes. It immediately cancels the response body/aborts without consuming events, creating reservations, mutating registry state or allocating work. HTTP401/403 or timeout retains a blocked resumable draft with existing-credential guidance; setup never asks for a token value.

The flow manages **one shared Ed25519 login identity** for all onboarded clusters: `dirname(clusters.json)/id_ed25519` and `id_ed25519.pub`, plus `dirname(clusters.json)/known_hosts`. These shared files live directly in `~/.config/worker-harness` by default, **not** in its `ssh/` subdirectory; `XDG_CONFIG_HOME` and `WH_CLUSTER_CONFIG` select the actual configuration parent. Connection-specific `config` and `bootstrap_config` remain under `ssh/<profile-id>/`; connection reuse may retain the first profile's config path. Keeping shared files outside `ssh/` avoids collisions with valid legacy profile IDs such as `id_ed25519` or `known_hosts`. Directories are 0700 and generated files 0600. Existing shared key/trust files are reused, never overwritten. A profile's `ssh_config_file` selects its config through OpenSSH argv `-F`, without editing `~/.ssh/config`. Alias mode preserves ordinary user config/ProxyJump/ControlMaster policy. `/etc/ssh/ssh_config` is explicitly included only when readable, regular, root/current-UID owned and not group/world writable; otherwise a UI warning directs required site settings into user config. Strict OpenSSH checks on user config are not weakened. Direct mode creates a unique `wh-<id>` alias with the supplied hostname/user/port and optional ProxyJump.

A newly generated shared private key is initially **unencrypted**; the dialog warns before generating it and never captures a passphrase. An existing shared key, including an encrypted one, is preserved. Add a passphrase in your own terminal with `ssh-keygen -p -f <printed-shared-key-path>` if desired, then unlock it through an accessible dedicated agent. **Read the sandbox restart/agent gate below before doing this:** the current launcher unsets `SSH_AUTH_SOCK`, so a host `ssh-add` does not by itself make the key usable inside this sandbox. BatchMode cannot unlock a key or answer MFA; resolve agent/site policy explicitly without weakening authentication.

Bootstrap and public-key installation commands are printed, **not executed**. Both the dedicated `config` and `bootstrap_config` explicitly use the shared configuration-parent `known_hosts` via `UserKnownHostsFile`. Its initial empty 0600 file is created only if absent; no user/global host-trust database is automatically copied, replaced or cleared. The first fenced command uses `ssh-copy-id` with the shared public key; the optional second command interactively verifies/adds the host to that same shared trust file. Both explicitly use `StrictHostKeyChecking=ask`, even when ordinary SSH policy is strict: independently compare the site's fingerprint before confirming it; `ssh-keyscan` alone is not verification. Read-only managed `ssh -G` evaluation and bounded `ssh-keygen -F -f` check effective hostname/port/HostKeyAlias, including hashed and non-default-port entries. An unprovable lookup or host-key probe failure shows the trust command. A new bootstrap preserves original key/agent/password/MFA authentication without the shared IdentityFile/IdentitiesOnly restriction; migration retains the old per-profile IdentityFile without IdentitiesOnly. Rerunning `/cluster-add <name>` uses the dedicated shared identity with strict host checking, then continues mapping/discovery on success. No authentication/trust bypass or automatic retry is introduced.

Command shapes (substitute the exact paths/alias printed by onboarding; these remain operator actions):

C16
```sh
ssh-copy-id -f -F '/absolute/configuration/directory/ssh/ibex/bootstrap_config' -i '/absolute/configuration/directory/id_ed25519.pub' -o StrictHostKeyChecking=ask 'EXACT_PRINTED_ALIAS'
```

```sh
ssh -F '/absolute/configuration/directory/ssh/ibex/bootstrap_config' -o StrictHostKeyChecking=ask 'EXACT_PRINTED_ALIAS' true
```

`ssh-copy-id -f` intentionally bypasses its default already-installed-key filter:
bootstrap may authenticate with an existing key, which would otherwise falsely
skip installing the shared key. Repeating the command can append duplicate
public-key entries.

An already running OMP process cannot inherit a newly selected agent environment. Under the current sandbox launcher, restarting OMP or merely exporting a host socket is insufficient; follow the dedicated-agent and full-sandbox restart gate below.

For IBEX, use the real login destination and independently verified site policy. Read-only discovery supplies candidate partitions/types/caps rather than guessing IBEX names; the review must preserve uncertainty about authorization and compute-node Tailnet reachability. A single cluster registration derives its selected CPU/GPU target profiles, so a second full onboarding form is unnecessary. Discovery verifies existing mounts, not mounts or transfers them; it does not install a runtime, build a SIF, grant account permissions, deploy a server or authorize charged work.

### Migrate existing per-profile keys explicitly

After the persistence/restart gate below, run this interactive OMP command:

```text
/cluster-ssh-migrate
```

If there is no shared key yet, select **one** existing wizard-managed legacy key for promotion and confirm. The migration exclusively copies its bytes into the shared path, preserving an encrypted key as encrypted; it does not generate a second shared identity, overwrite an existing shared key, or delete legacy keys. If a shared key already exists it is reused. Only recognized wizard-generated managed configs are migrated; external/unrecognized configs are explicitly skipped rather than guessed or overwritten. Review the command's reported migrated/skipped profiles.

Migration rewrites recognized dedicated configs to the shared identity/trust while retaining their alias/direct destination policy. Each migrated bootstrap config retains its **old per-profile IdentityFile without IdentitiesOnly**, alongside shared host trust, to authorize installation on hosts that accepted only the old key. It prints the same fenced public-key installation command and, when needed, interactive trust command for each migrated profile. A cluster previously authorized with a different profile key needs the **shared** public key installed; updating local config alone cannot authorize it. Host trust is not imported automatically: verify each host interactively using the printed bootstrap command and an independent trusted fingerprint. Keep the old files until all required hosts pass the strict shared-key probe. Merely adding sandbox path entries does not migrate existing profiles.

### Persistent sandbox configuration and restart gate

The interactive operator's default agent-sandbox allowlist is `~/dotfiles/agent-sandbox/.config/agent-sandbox/paths`. Its two Worker Harness entries are plain paths: **`~/.config/worker-harness`** (profiles, managed login key/configs, host trust and any enrollment credential stored there) and **`~/.local/state/worker-harness`** (submission journals, scoped tokens and notification cursors). All entries use the existing ordinary path parser; unrelated legacy entries are unchanged. Fleet launches do not consume this default file: [`src/worker_harness/sandbox.py:25–31,41–48,66–73`](../src/worker_harness/sandbox.py) defines and renders `ROLE_PATHS` without these credential directories and sets `AGENT_SANDBOX_PATHS` to the session-specific file. [`src/worker_harness/orchestration.py:450–466`](../src/worker_harness/orchestration.py) generates and writes that file before launch. The separation is the selected allowlist, not role-dependent path syntax. A manually launched process using the operator allowlist receives its ordinary binds regardless of `WH_SESSION_ROLE`; this is not hostile-user isolation. Allowlist changes do not alter existing sandbox mounts; absent host source directories are skipped, not created.

For the interactive operator's next host launch, invoke **`"$HOME/dotfiles/agent-sandbox/.local/bin/agent-sandbox"`** with the usual tool/binary arguments and select **`AGENT_SANDBOX_PATHS="$HOME/dotfiles/agent-sandbox/.config/agent-sandbox/paths"`**, or use the host's existing stow/symlink installation pointing to that launcher and allowlist. The entries require no new launcher syntax. This session has not established the host's active launcher/config symlinks. Do not override the generated fleet session allowlist with the operator default.

Before the next sandbox launch, run this **in a host terminal outside the existing sandbox**, using the host account that launches it:

```bash
mkdir -p "$HOME/.config/worker-harness" "$HOME/.local/state/worker-harness"
chmod 700 "$HOME/.config/worker-harness" "$HOME/.local/state/worker-harness"
```

Do not create these in the current masked sandbox HOME and assume they exist persistently on the host. The current sandbox's missing default configuration directory does not establish whether the host already has profiles, keys or journals; inspect those only from the host terminal, without exposing secrets.

With custom `XDG_CONFIG_HOME`, `WH_CLUSTER_CONFIG`, `XDG_STATE_HOME`, or `WH_CLUSTER_STATE_DIR`, persist the **actual** configuration/managed-SSH and state locations instead: add their ordinary host paths to the interactive operator allowlist, create their host directories with private permissions before launching, and preserve the overrides in the new session. Keep credential paths and broader credential-containing parents out of the separate generated fleet allowlist. The two default entries alone do not cover arbitrary override paths.

**Stop here for restart:** fully exit and relaunch **agent-sandbox**, then start OMP inside the new sandbox. Restarting only OMP cannot apply the new mounts. Existing legacy profiles also require the explicit SSH migration above; mounting new directories alone cannot fix stale `ssh_config_file`, key or known-host paths. Do not rerun onboarding or attempt live SSH from the old sandbox to work around missing mounts.

The launcher currently unsets `SSH_AUTH_SOCK`. An encrypted login key therefore additionally requires a deliberately provisioned **dedicated** agent/socket made accessible to the new sandbox and explicitly selected for its SSH client. Merely running `ssh-add` in a host shell, restarting OMP, or restarting the unchanged launcher does not make that agent accessible. Do not forward the general host agent or change launcher/forwarding policy as part of this migration. Without dedicated-agent access, a passphrase-protected key is a visible prerequisite failure for BatchMode, not a reason to weaken authentication.

### Submission and recovery sequence

1. Validate current live inventory, resources, paths and shared identity; generate/persist a submission key and canonical request digest.
2. Reserve a real OFFLINE worker with scoped registration token hash; persist its initial ordinary queued job with matching submission key. Idempotent same-key/same-body requests recover the same worker/job; changed payload conflicts. Never sbatch without confirmed attached useful work.
3. Stage private run files and small root-owned runtime assets at `<shared_root>/.wh-slurm/<worker_id>`, then submit once through local strict OpenSSH. Remote flock, attempt marker, and atomic `submitted.json` fence retries. Patch `submission_attempted` before sbatch. Inherited `SBATCH_*` and dangerous Slurm option variables are removed; use `SLURM_UMASK=077` and `--export=NIL` while retaining site authentication/runtime environment.
4. Registration on 12888 must authenticate the reserved identity/capacity. Actual resource mapping and orchestrator-to-worker Tailscale SSH readiness gate ONLINE/queue dispatch. A Tailnet IP alone is insufficient. Startup/enrollment is bounded by 180 seconds.
5. Queue-managed useful work runs through the existing daemon/JobManager/tmux/runner. CPU jobs have zero GPUs, empty CUDA mask, and serialize one at a time on CPU Slurm targets; arbitrary fleet zero-GPU enqueue is not enabled. GPU assignments preserve Slurm visibility across cleanenv and resolve physical UUIDs; missing/ambiguous/MIG mappings fail visibly. CPU mode omits `--nv` and CUDA readiness. CPU/memory reports reflect allocation limits.
6. Normal success with no useful queue/running work atomically closes admission (DRAINING), then exits. Failed queued work permits only the configured bounded failure grace; zero means no idle holding. Ordinary exec diagnoses but does not extend grace. An actually starting queued CPU/GPU rerun clears it. The deadline derives from runner finish time and survives reconnect/outage. Immediate diagnostic exec is not useful queued work.
7. Scheduler polling reports raw states/reasons/timestamps and recovered structured job results before terminal reconciliation. Confirmed results cannot be rewritten by terminal accounting or stale observations. SSH failure, missing squeue entries, or heartbeat loss is not completion. Completed/reserved worker history survives pruning, but finished/DRAINING targets reject admission with `409 SLURM_WORKER_FINISHED`; use fresh cluster enqueue.

On uncertainty, retain the returned/generated `submission_key` and inspect ordinary worker/job/scheduler evidence. Retrying the same request/key reads journal/remote evidence and exact owned scheduler identity; it never blindly resubmits after an attempt marker. Multiple matches require a validated `candidate_job_id` from evidence; candidate selection is excluded from the digest and requires an existing key. Read tools never bind/submit. A new key intentionally means a new experiment, not recovery of the unknown one.

`stop_job` defaults to `scope: "job"`; other useful queued/running work is preserved. Cancelling the last pending job can atomically close/cancel an empty not-yet-started allocation. `scope: "allocation"` derives/validates the scheduler allocation from the job, closes admission and requests local scancel; response means requested until terminal accounting. This scope is rejected for non-Slurm workers. Initial GPU count/worker reassignment freezes once submission is attempted: cancel/fresh enqueue to change allocation resources. Never perform broad name-based scancel.

### Runner, failure grace, and signals

`src/worker_harness/job_runner.py` is the shared standalone primitive, not another allocation supervisor. `run --job-dir PATH` is a Linux child subreaper, writes output plus atomic runtime/result evidence, and proves descendants exited before release. `control --job-dir PATH --action stop|checkpoint --signal USR1|TERM` uses a private socket and verified pidfds; stop uses TERM, two-second grace, then KILL. Missing proof retains claims; printed `EXIT:` text is not proof.

The finite shell wrapper owns traps, a background child and interruptible wait. USR1 warning closes admission and forwards the workload-declared checkpoint signal. TERM is sticky and dominates later checkpoint signals, bounds cooperation by site termination grace, then stops/reaps. Persistent control files cover pre-daemon signals. Checkpoint saving/resume is application code with shared paths; forwarding a signal never proves a checkpoint exists. Site preemption can give less/no warning. Useful queued work can finish during outages, but unknown remote queues do not authorize idle holding or extend persisted failure deadlines. Requeue/repeated launch markers are rejected. There is no successor sbatch.

### CPU/GPU resource sizing

Live `sinfo --Node`, named-field `scontrol --oneliner show nodes` and partition policy drive sizing. Exact partition/GPU type and simple feature or `&` conjunction constraints filter eligible configured nodes. Busy eligible nodes still count for sizing; availability/free resources are a separate timestamped observation. Missing/nonpositive/ambiguous/MIG capacity fails instead of guessing. Optional IBEX `ginfo` is bounded supplemental availability, never the capacity source or prerequisite.

For requested GPUs `g`, require `1 <= g <= max_gpus` and nodes with at least g of that type. For node i, C is configured schedulable CPUs, M is RealMemory minus MemSpecLimit (MiB), and G is configured physical GPUs. Defaults are `cpus=max(1,floor(g*min(C/G)))` and `memory_mb=256*floor(g*min(M/G)/256)`. Thus an 8-GPU/64-CPU/524288-MiB node yields 8 CPUs/65536 MiB for one GPU, 16/131072 for two, independent of current free capacity. Heterogeneous nodes use conservative minima, not a largest-node/average guess.

CPU defaults are 1 CPU/4096 MiB with no GPUs. Profile/partition CPU caps apply first, then RAM caps including final CPUs times MaxMemPerCPU. Computed defaults may cap/round down; explicit impossible requests fail, never silently shrink. Require a matching node able to fit the final request and bound explicit walltime by profile/partition MaxTime. Unknown account/QoS restrictions remain unverified until Slurm responds. Fresh SSH/inventory failure blocks submission.

Emit exactly `--nodes=1 --ntasks=1 --cpus-per-task=<n> --mem=<MiB>M`, plus `--gpus-per-node=<type>:<g>` only for GPU work, explicit time, `--parsable --no-requeue --export=NIL`, unique name/comment and shared logs. Do not use exclusive, `--mem=0`, or mixed per-GPU/per-task CPU/RAM forms.
