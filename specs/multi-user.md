## Context
Implement multi-user Worker Harness in a new branch and separate worktree, including the extension submodule. Provide local web accounts, self-service API keys, web-only user/key administration, ordinary-user tunnel and Marimo controls, a shared FIFO job board, non-sorting priority and duration estimates, permissioned resource ownership, audited shared reordering, and per-user/per-worker usage totals. CPU setup work runs alongside GPU jobs; a GPU job with 600 seconds of observed non-display-workload inactivity is stopped when GPU work is waiting, and its allocation is released only after confirmed termination.

The deployment is a trusted team sharing one runtime, OS account, code, and data per worker. API privacy is enforced, but shell jobs are not isolated from shared files/processes; keep host-managed storage/mounts unchanged, without adding per-user containers or a network-storage/rclone rollout. Existing Pi orchestration remains a separate bootstrap-administrator workflow, not a multi-user project/chat feature.

## Grounded implementation findings
- `src/worker_harness/heartbeat.py`, `require_role` and `require_api_caller`: shared operator bearer resolves to `None`; Pi-session bearers resolve to sessions; anonymous compatibility and separate WebSocket checks exist. Replace this sentinel model, not merely add a username header.
- `src/worker_harness/db.py`, `insert_queued_job`, `claim_queued_job`, `update_pending_job`: durable SQLite FIFO exists. Claim already checks FIFO head and allocation overlap. Reorder reads precede its first write and its lock is process-local; use explicit transactions for revision/ordering/audit atomicity.
- `src/worker_harness/job.py`, `JobManager`: immediate CPU/setup and queued GPU entry points exist. `Job` in `models.py` lacks human ownership, priority, and usage attribution.
- `src/worker_harness/ssh.py`, `_build_job_command`, `ssh_tmux_kill`, `ssh_tmux_running`: command execution and completion currently depend on tmux and a text `EXIT:` log marker. Killing tmux does not establish that descendants have exited.
- `worker_container/worker_daemon.py`, `get_gpu_info`/`_gpu_process_usage`: existing `IGNORED_GPU_PROCESS_NAMES` contains xorg, xwayland, gnome-shell, kwin_wayland. Keep that display-server exclusion for idle detection, but not the existing blanket exclusion for all processes below 512 MiB. Query failures currently can appear empty; default heartbeat is 60 seconds. Do not reuse `busy == false` as the idle criterion.
- `web/app.js`, `api`, `route`, and `web/index.html`: static same-origin/hash-route Pi UI, no login or job board. `web_container/nginx.conf` and `40-wh-operator-auth.sh` inject shared operator credentials. `web/sw.js` excludes `/api/` from caching; retain that property.
- `.gitmodules` identifies `extensions/pi-worker-harness` as a separate Git repository. At planning time root is on `main`; that submodule is detached with user modifications in `README.md`, `SPEC.md`, and `widget.ts`. Preserve them. The source root was `/home/dome/Work/worker-harness`.

### S1 — Human identity, browser sessions, API keys, and bootstrap
Reuse SQLite migration conventions in `Database.connect`, session random-token/hash-at-rest issuance in `orchestration.py`, and existing FastAPI dependencies. No user/password/browser-session implementation exists; introduce `src/worker_harness/auth.py` for auth services and `src/worker_harness/auth_routes.py` for the following web routes rather than extending the large route factory with all credential logic.

Persist:
- `users`: UUID `id`, case-normalized unique `username`, `display_name`, Argon2id `password_hash`, boolean `is_admin`, boolean `disabled`, `created_at`, `updated_at`. Username is lowercase `[a-z0-9][a-z0-9_-]{2,63}`; display name 1–100 characters. No hard-delete endpoint.
- `api_keys`: UUID `id`, `user_id`, `label` (1–80 characters), unique SHA-256 `token_hash`, nonsecret `prefix`, `created_at`, nullable `last_used_at`, nullable `revoked_at`. Generate `whk_` plus `secrets.token_urlsafe(32)`; reveal the full key only in the issuance response. Keys do not expire automatically in this implementation; revocation/disabled-user checks are made on every request.
- `web_sessions`: independent UUID `id`, unique SHA-256 `token_hash`, `user_id`, independent random `csrf_token`, `created_at`, absolute `expires_at`. Expire after 12 hours; logout/password reset/account disable deletes applicable sessions. Store neither plaintext passwords nor raw session/API credentials.
- One singleton identity-settings row storing immutable `bootstrap_user_id`.
- `owner_user_id` on jobs, Pi sessions, port_forwards and marimo_sessions, indexed and required after bootstrap backfill. Add created_by_actor_id to tunnel/Marimo records. Backfill existing records to the bootstrap administrator; finer historical ownership cannot be reconstructed. Retain internal Pi-session hashes/relationships, remove shared operator authentication, and recreate legacy unauthenticated Marimo listeners before exposing them to new users.

Add `argon2-cffi` to `pyproject.toml` and use `argon2.PasswordHasher` with Argon2id defaults, `check_needs_rehash`, and `verify`; passwords are 12–1024 characters, never trimmed/logged. Run hashing/verification off the event loop. Use a dummy hash check for unknown users and generic login failures. Rate-limit failed login attempts to five/minute per username and per trusted client address, returning 429 with Retry-After; do not trust arbitrary forwarded-IP headers.

Add `bootstrap-admin --username NAME` to `python -m worker_harness.orchestrator` in `orchestrator.py`. Prompt twice without echo; do not accept passwords in arguments/environment. It uses configured `WH_DB_PATH`, atomically creates the first admin/settings row and backfills owners; return nonzero if bootstrap already exists. Startup may initialize schema and serve login/health/static assets without a bootstrap account, but every protected request is denied and no jobs dispatch until bootstrap finishes. Do not create default credentials. Block disabling/demoting the bootstrap user or removing the last enabled administrator with 409; keep the legacy Pi owner stable.

Define a concrete `Principal` in `auth.py` with `user_id`, `credential_kind: Literal['api_key','web_session','pi_session']`, `actor_id`, and optional `pi_session`. `resolve_principal(connection: HTTPConnection) -> Principal` resolves explicit bearer first (invalid bearer never falls back to cookie), otherwise browser cookie. Disabled user always fails. No valid auth means 401, never `None` authority. `require_web_user`, `require_web_admin`, and `require_bootstrap_web_user` reject bearer credentials, including an admin user's API key, with 403.

Derive nonsecret actor IDs exactly as `api_key:<api-key UUID>`, `web_session:<web-session UUID>`, or `pi_session:<PiSession UUID>`. Never use a credential/hash as an actor ID. Historical migrated jobs use `migration:<bootstrap-user UUID>`. Preserve actor strings in jobs/audits when credential rows are revoked/deleted; preview ownership is per credential instance, so a different browser login or key cannot commit it even for the same user.

Web routes and exact behavior:
- `POST /api/v1/auth/login` `{username,password}` → `{user,csrf_token}` plus session cookie; wrong credentials → generic 401.
- `GET /api/v1/auth/me` → `{user,csrf_token}` for browser sessions only; this is how reload reconstructs state.
- `POST /api/v1/auth/logout` → 204, revoke current cookie and expire it.
- `POST /api/v1/auth/password` `{current_password,new_password}` → 204, revoke all own sessions and require login again.
- `GET/POST /api/v1/auth/keys`: list safe key metadata / issue own key with `{label}` → `{key,token}` (201, token once). `DELETE /api/v1/auth/keys/{id}` revokes an owned key, 204; another owner's key → 404.
- `GET/POST /api/v1/admin/users`: list users / create `{username,display_name,password,is_admin}` (201).
- `PATCH /api/v1/admin/users/{id}` accepts only `{display_name?,disabled?,is_admin?}`; duplicate username on creation → 409, malformed input → 422. Disable revokes all keys and sessions immediately, cancels that user's pending jobs as `user_disabled`, and does not kill running jobs; running work finishes or follows the same idle policy. Re-enabling does not revive credentials/jobs.
- `POST /api/v1/admin/users/{id}/password` `{password}` resets password, revokes sessions, returns 204.
- `GET/POST /api/v1/admin/users/{id}/keys` lists safe metadata / issues an ordinary key for that user; `DELETE /api/v1/admin/users/{id}/keys/{key_id}` revokes. Disabled users cannot receive keys (409).

Safe user responses contain only id, username, display_name, is_admin, disabled and timestamps; never password_hash. Safe key responses contain id, user_id, label, prefix, created_at, last_used_at, revoked_at; never token_hash. Bootstrap display_name defaults to username. Apply browser-route dependencies explicitly so the global auth gate allows unauthenticated login and static assets but not key/admin routes. Public `/health` returns only status/timestamp, removing current session-ID/attachment diagnostics from its unauthenticated response. Login failures, validation errors and audit records must not echo supplied passwords/keys.

All admin endpoints require an admin browser session; key-management endpoints require browser sessions, not keys. Inaccessible private objects return 404. Sessions use wh_session, HttpOnly, SameSite=Strict, Path=/, Secure except explicit loopback HTTP development. Require WH_WEB_ORIGIN as one exact external origin; reject non-HTTPS except localhost/127.0.0.1/[::1]. Cookie-authenticated harness mutations require matching Origin and X-CSRF-Token; login requires Origin without a pre-login token. Native Marimo proxied browser mutations use S2a's narrow Origin/Sec-Fetch-Site rule because its frontend cannot send the harness CSRF header. WebSocket cookies require matching Origin. No permissive CORS. Auth/API responses are no-store; credentials never enter URLs, logs, localStorage, service-worker caches or workload environments.

### S3 — Job schema, CPU/GPU behavior, privacy, and usage
Extend `Job` and DB persistence with `owner_user_id`, `submitted_by_actor_id`, immutable `submitted_at`, immutable globally monotonic `submission_sequence`, `priority` enum `flexible|normal|blocking|time_critical` (default `normal`), public `priority_note` (max 1000 characters), nullable `deadline_at` (UTC epoch seconds), nullable `termination_reason`, and worker-name snapshot `worker_name_at_submission`. `name` is explicitly a public queue label. `time_critical` requires a nonblank priority_note; no other level needs one. Neither priority nor deadline changes FIFO. Keep existing `expected_seconds` as a soft estimate and `gpu_count` for resource requests; no time-limit inference.

Keep current route split: `POST /api/v1/jobs` launches CPU/setup immediately with `gpu_count=0`; require positive expected_seconds and nonblank name on the new contract. `POST /api/v1/jobs/queue` requests positive gpu_count and queues GPU work. Validate worker existence and capacity; CPU submission to offline worker returns 409 rather than pretending it launched; GPU work may queue offline with unavailable ETA. Both routes accept priority/note/deadline; current sync/no_pty semantics remain for CPU callers. Always pass explicit GPU indices to launch: [] for CPU → empty CUDA_VISIBLE_DEVICES, assigned indices for GPU. This is cooperative isolation, not device ACL enforcement; users can defeat it in the agreed shared runtime.

CPU jobs never consume queue slots or wait behind GPU jobs. Maintain strict FIFO per worker; queue insertion order is submission sequence, while queue_order is editable pending order. A blocked head continues to block later heads; no backfill, automatic priority sorting, preemption, quotas, or fair-share enforcement.

Split metadata edit from shared reorder. Existing `PATCH /api/v1/jobs/{id}/queue` becomes owner-only pending metadata edit of `name`, `expected_seconds`, `gpu_count`, `priority`, `priority_note`, `deadline_at`, and optional `worker_id`; remove `position` from it (extra fields → 422). Running owners may revise expected_seconds/priority/note/deadline through new `PATCH /api/v1/jobs/{id}` only; no command/worker/GPU reassignment while active. Submit a new job to change a command.

Add owner-only `GET /api/v1/jobs/{id}` for private detail. Use positive expected_seconds on public CPU/GPU submission; internal setup creators without an estimate pass 0 explicitly, which displays as unknown, not zero runtime. Extend `start_job` with keyword `expected_seconds: int = 0` and the new priority fields, preserving existing internal names; require callers without a public name to use a neutral `Setup job`, never derive public names from command text. Browser/extension/CLI user submissions collect actual estimates instead of silently choosing one.

`GET /api/v1/jobs` returns only owned jobs regardless of filters. Job details and log endpoints, including SSE, and DELETE require ownership for every credential kind; admins have no override. Another user's private job → 404. Revalidate revocation/disabled status before each streamed log batch. Return 409 for invalid lifecycle changes and 503 if worker unreachability prevents confirmed stop; do not report successful cancellation or release capacity on uncertainty. Use `termination_reason=user_cancelled|gpu_idle_timeout|user_disabled` for these terminal paths while retaining existing done/failed status conventions.

Usage endpoint `GET /api/v1/usage?worker_id=&user_id=` returns shared aggregates grouped by immutable owner ID and worker ID with display-name snapshots: `job_seconds`, `cpu_job_seconds`, `allocated_gpu_seconds`, `running_jobs`, `as_of`, and `provisional` boolean. Define job_seconds as sum(max(0, terminal_or_now - started_at)) for jobs actually admitted/started; CPU subset has gpu_count=0, allocated GPU seconds multiply admitted duration by gpu_count. Waiting jobs contribute zero. This measures allocated wall/GPU time, not GPU utilization or actual CPU core-seconds; label it accordingly in UI. Active/unknown-terminal allocations are provisional and keep accruing until confirmed release. Record timing/release transitions once in the same DB transaction as status and revision updates. Legacy totals belong to bootstrap owner and are labeled historical estimates. Do not delete jobs/usage when a worker is pruned; preserve worker-name snapshot and use a left join for absent workers. Adjust `Database.delete_worker`'s existing job deletion accordingly.

- Preserve root/submodule source modifications and use suffixed new worktrees if names collide. If a required Linux supervisor primitive or GPU telemetry field is unavailable, fail launch or keep telemetry unknown/reservations held as specified; never silently downgrade to tmux-only termination or optimistic idle release.
- Live fleet rollout is not part of development authorization. Finish all local implementation and smoke proof; leave production migration/real-GPU acceptance explicitly unverified until a spare-worker rollout is authorized. Do not weaken privacy or stop confirmation to make unavailable hardware appear tested.
